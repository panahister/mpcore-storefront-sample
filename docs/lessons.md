# What building this taught

Storefront was the first place a backend generated by MP Core actually **ran**: it started, took real
tokens, sent messages across queues and brokers, and wrote an audit trail. Much of what follows could not
have been found by reading code, and none of it had been.

Two rules were kept throughout:

1. A defect of MP Core is fixed in MP Core, never worked around in the sample.
2. A guarantee is proved by a test that was **seen failing** without the fix, or by an experiment against
   the running system. A sentence in a document proves nothing.

The first part lists what was wrong in MP Core and is fixed in version `0.9.0`. The second lists what was
wrong in the sample's own design, because those mistakes are the ones a team is most likely to repeat. The
third lists what is still open.

## 1. Defects found in MP Core, fixed in 0.9.0

### A message could leave without the change that caused it

- **How it was found.** Somebody asked what guarantees that an event is not published when the save
  fails. The tests covered a handler that throws and a handler that answers a failure, not a save that
  fails. So one basket was checked out eight times at the same moment, three times over: 3 checkouts were
  accepted, 21 were refused, and **16 orders** existed afterwards, 11 of them charged.
- **Cause.** Every attempt emptied the basket and published "basket checked out"; the database let one
  commit. The host retries a save that lost a race. For an invoked command Wolverine retries on the same
  message context, which still held the message of the failed attempt, with a new unit of work. The retry
  found the basket empty, changed nothing and answered a failure; its empty save committed, and the commit
  released the message. The idempotency key was stored too, with the answer of the attempt that had
  failed.
- **Fix.** `HandlerAttemptMiddleware`: an attempt that did not run to its end, the save and the commit
  included, is cleared. Its messages are discarded and the idempotent operation forgets its answer.
- **Proof.** `RetryAfterFailedSaveTests` in two test projects, seen failing before the fix. Scenario S15.
  The same experiment after the fix, five times over: 44 saves failed, 5 checkouts were accepted, 5 orders
  exist.

### A generated backend had no health check

- **How it was found.** The warehouse service serves gRPC only. Asked for its health, it answered
  `UNKNOWN`. So did Commerce, on its gRPC port.
- **Cause.** The template mapped the probes and registered no check. `grpc.health.v1.Health` answers
  `SERVING` only when a check ran and none failed, so a probe read every backend as not serving. On REST,
  `/health/ready` answered `Healthy` without having asked anything.
- **Fix.** The template generates `Hosting/HostHealthChecks.cs`: a check for the process, tagged `live`,
  and one for the database, tagged `ready`. *Alive* asks the first only.
- **Proof.** With PostgreSQL and TimescaleDB stopped: alive stayed healthy on all three backends, ready
  answered 503 and `NOT_SERVING`; started again, ready recovered. A template test holds the registration.

### A host with business audit could not start, and its handlers failed at the first message

- **Cause.** Wolverine registers the context options as a singleton, so that it can generate handler
  code inline; the audit interceptor was scoped, and the audit sink took `IServiceScopeFactory`, which a
  handler's dependency graph must not contain.
- **Fix.** The current-actor accessor, the tenant context, the audit context and the audit interceptor are
  singletons that read ambient state on every call. A detached audit write goes through a connection of
  its own. A public constructor was removed for it.
- **Proof.** `AuditInterceptorLifetimeTests`, `AmbientAccessorLifetimeTests`, `HandlerGraphConstraintTests`.

### Work done by a queued handler was audited as anonymous

- **Cause.** A handler does not save; the middleware saves after the handler returns. An actor scope the
  handler opens is closed by then.
- **Fix.** `HandlerActorMiddleware` wraps the whole execution, the save included, in a system actor named
  after the message (`system:ReserveStock`). An actor that already exists is left alone.
- **Proof.** `HandlerActorTests`. In the sample no anonymous audit record remains.

### The host project's own handlers were never discovered

- **Cause.** Wolverine infers its application assembly from whoever called `UseWolverine`. MP Core makes
  that call for the host, so the inference landed on MP Core itself.
- **Fix.** `WolverineFoundationOptions.ApplicationAssembly`; the template passes `typeof(Program).Assembly`.
- **Proof.** `ApplicationAssemblyTests`.

### Validators ran after the handler

- **How it was found.** A checkout with a card number instead of a token answered 500: the handler ran
  with a null address, and the validator fired afterwards.
- **Cause.** The rollback policy added its frame to the middleware that runs before the handler, and
  relied on the frame's dependency on the handler's result. The code generator satisfies such a dependency
  by moving the handler call up, ahead of every middleware registered later.
- **Fix.** The frame is the first post-processor of the chain.
- **Proof.** `FluentValidationUnderFoundationTests`, seen failing.

### A business rule reached the caller under a generic code

- **Cause.** A rule carried a code and a developer's message, but no error domain and no message key.
  Both transports mapped every broken rule to one generic identity.
- **Fix.** `BusinessRule`, with an error domain, a code, a message key and arguments. REST and gRPC report
  a broken rule under its own identity. A queued message that breaks a rule is never retried.
- **Proof.** `BusinessRuleTests`, the transport tests, `BusinessRuleRetryTests`. Scenario S3.

### A backend without business audit could add no migration once it had an inbox

- **How it was found.** Analytics has no business audit. It was given the inbox, and `dotnet ef` stopped
  before it read any migration.
- **Cause.** The template wrote a design-time context factory only for a backend with business audit.
  Request idempotency and the inbox attach an interceptor to the context as audit does, and are added by
  hand, after the backend was generated.
- **Fix.** The template writes the factory for every backend.
- **Proof.** A backend generated without audit, built against the packed packages: a migration was added
  with `ConnectionStrings__PostgreSql` set, and refused with a clear message without it.

### Smaller ones

| What was wrong | Fix |
|---|---|
| `Microsoft.EntityFrameworkCore.Relational` resolved to an older patch than EF Core | pinned in three packages; `EntityFrameworkVersionAlignmentTests` |
| No Wolverine metric was exported: Wolverine names its meter `Wolverine:<ServiceName>` | the meter is matched by prefix; `WolverineMetricsTests` |
| A generated project could not build on Apple Silicon without Rosetta | the template uses a native `protoc` when one is installed |
| The modular-monolith template generated three projects per module and two empty root projects | one project per module (ADR-012) |
| Two rules of Wolverine that only show at run time were undocumented: register adapters by type, never with a lambda; name a handler class `...Handler` or `...Consumer` | both are in the module guide and in the skills |

## 2. What MP Core did not have, and has now

| What was missing | What was added | Why it matters |
|---|---|---|
| Request idempotency | `IIdempotentExecutor`; the `Idempotency-Key` header on both transports. The key, a hash of the request and the answer are written in the save that commits the change. | A client that retries a `POST` after a timeout cannot know whether the first attempt succeeded (RFC 9110). |
| An inbox for consumers | `UseMPCoreInbox()`; every integration event travels with its identity as the idempotency key. | The outbox delivers at least once, so a consumer sees some messages twice. |
| Input validation | `MPCore.Validation.FluentValidation`: validators run before the handler and answer one violation per field. | Every handler checked the shape of its request by hand, each in its own way. |
| Messages a person can read | `MPCore.Localization`: a message catalog over resource files, and translations edited at run time. | Every failure carried a message key, and nothing ever rendered one. |
| Rules for queries | The module guide and the skills say what a query may do. | The sample had a `GET` that acknowledged a price change, and queries that read through the write model. |

## 3. Mistakes in the sample's own design

These are not defects of a framework. They are decisions that looked reasonable, worked, and were wrong.

### Checkout changed three modules in one transaction

Ordering emptied the basket and registered the payment through interfaces the other modules published,
inside its own transaction. It worked, because the modules share a database; and that one transaction is
exactly what has to be redesigned on the day a module becomes a service.

**Now:** checkout is a command of the Basket. It empties the basket and publishes a snapshot of what it
held, in a transaction that changes one module. Ordering creates the order from the message.
**The cost:** the answer is "accepted", not "created", and the Basket has to refuse at the edge what
Ordering would refuse later. `CheckoutContractTests` holds the two together.

### A failed checkout wrote the card token and the shopper's phone number into the log

Wolverine logs a message whose handling failed by printing it, and a C# record prints every property.

**Now:** a message that carries something personal or secret overrides `ToString`. An architecture test
builds every message that has a property named like a secret and reads what it prints.

### The card token outlived the payment in the queue tables

After checkout became a message, the token travelled in two messages between modules. A handled envelope
stays in the queue tables for a while, and a dead letter stays until an operator removes it.

**Now:** a payment intent. The storefront hands the token to Payments first and receives an identity;
checkout and every message carry the identity. It is the payment intent of the card providers' own APIs.
Scenario S17 reads the queue tables and finds no token.

### Under contention for one product, an order stayed "submitted" for ever

Twelve orders for one product within a few seconds: 5 were paid, **7 lost the race four times**, went to
the error queue, and stayed where they were. The shopper had been told "accepted".

There were two causes. The retry paused 50, 200 and 500 milliseconds, the same for every message, so the
losers of one collision came back together and collided again. And a command that ends in the error queue
answers nothing, so a process that waits for its answer waits for ever.

**Now:** eight retries with growing pauses, each lengthened at random (Marc Brooker, *Exponential Backoff
And Jitter*). And giving a message up is itself an answer: the host tells the order process, which cancels
the order, voids the payment and releases the stock request. Scenario S16. The answer was forced once with
a build that retried once after one millisecond: 9 of 12 requests were given up, and all 9 orders were
cancelled, their payments voided and their reservations released.

### Restocking twice added the stock twice

The delivery note went to the audit trail only. A double click added the same delivery twice, and the
store then sold stock that did not exist.

**Now:** the delivery note is a business key, unique per product. A request key would not have helped:
the same note entered twice arrives with two different keys. Only the product knows that the note itself
is the identity.

### The warehouse's news could arrive about an order that had already left

A paid order can be shipped through Commerce's own gRPC door as well as by the warehouse service. The
second report for the same order broke the rule about an order's status, and the message was given up:
it went to RabbitMQ's dead-letter queue, for an operator to read and find nothing to do.

**Now:** the consumer accepts news about something that is already so, and changes nothing. The inbox
cannot do this: it knows whether it has seen an event, not whether the event still says anything new.
Scenario S18 ships one order by both doors and counts the dead-letter queue; it was seen failing without
the change.

**Worth knowing:** a message that arrived from RabbitMQ and is given up goes to the broker's own queue,
`wolverine-dead-letter-queue`, not to the table `wolverine.wolverine_dead_letters`, where a given-up
message of a local queue goes. An operator has two places to look.

### An AI agent found no skill at the root of this repository

Each backend carries MP Core's skills, and an agent that is started in a backend's folder finds them.
Started at the root, Claude Code and Codex both found none: each looks for skills from the folder it is
started in, and neither looks into the folders below at the start. Nobody had asked the agents.

**Now:** the root has ten skills of its own. Each finds the backend a task belongs to and hands over to
that backend's skill. Both agents were asked again, and both were then given one real task:
[building-with-ai-agents.md](building-with-ai-agents.md).

### A price was shown without its cents

A broken rule told the caller "from 485 to 4850" after prices had become dollars and cents: the rule
still printed whole numbers, and a price of 459.50 would have been shown as 460.

**Now:** the rule prints the amount as it is. It was found by drawing the picture of a message for the
front page, and comparing it with what the code would print.

## 4. Still open

Nothing here is a defect that loses data. Each is a limit to know, or a decision MP Core has not taken.

| Subject | State |
|---|---|
| A process that stops between a commit and the delivery of its messages | Relies on Wolverine's recovery of durable envelopes. Neither MP Core nor this sample has a test of it. |
| The eraser of unused payment intents | Has unit tests and no end-to-end test: an intent lives thirty minutes. |
| The name of an integration event is not the name the broker carries | Two services that share no assembly use one channel per contract, and the listener names the type it reads (`DefaultIncomingMessage<T>()`). A mapping from the event's name would remove that line. |
| A message with no route is dropped with a log line at Information | A naming mistake lost a message silently during development. A warning, or a failure at startup, would have shown it. |
| `IMessagePublisher` cannot set a partition key or a delay | Commerce sets the Kafka key in its host. A payment deadline is impossible without scheduling. |
| Only the stock request answers when it is given up | The other steps of the order process do not yet. A process with a deadline would cover all of them, and needs scheduling. |
| The hybrid cache gives its in-process level the same lifetime as Redis | With several instances, the others stay stale after an eviction until the entry expires. |
| A secret in a message is kept out of the log by the product, not by MP Core | MP Core's redaction works on log attributes and cannot see inside a printed message. |
| EF Core logs a harmless error while applying the first migration to an empty database | It reads the history table before it creates it. |
